# Audit #276 — List & Pagination Review (apps/web + apps/backend)

**Scope:** every page/component that renders a list of records, and every list-returning route under `apps/web/app/api` and `apps/backend/src/routes`. For each: the source query, its row limit / `.range()` usage, whether results can be silently cut off, and how (if at all) the user would know. No fixes applied — report only.

**Background pattern (reference, already correct):** `fetchImpactRows` in `apps/web/app/api/signals/driver-breakdown/route.ts` pages through `.range(from, from+PAGE_SIZE-1)` in a loop until a page returns fewer than `PAGE_SIZE` rows — this is the only way to get a true complete result set past PostgREST's default 1000-row-per-request cap. The same loop pattern is reused in `apps/web/lib/signal-outcomes-server.ts`, `apps/web/app/api/signals/source-stats/route.ts`, `apps/web/app/api/prices/history/route.ts` (the `days` branch), and `apps/backend/src/routes/accuracy.routes.ts`. Anything below using a bare `.limit(N)` (no loop, no `.range()`) with N capable of being exceeded by real data is a cut-off candidate.

## Summary

- **Rows with a "silent cut-off" verdict: 10** (across both tables, counting the frontend surface and its backing API route as separate rows where both appear). One of the 10 (`GET /api/signals/[id]`) is a pointer row that cross-references the frontend table rather than a distinct new issue.
- **Distinct underlying silent-cut-off issues: 7** — (1) Alerts page / `GET /api/alerts/recent` (100-row fetch, no pagination beyond it), (2) Related Events panel on the event detail page (50-row candidate cap, no "more" indicator), (3) Signal Chat panel / `GET /v1/signal-chat/:id/chat` (50-message hard cap, no older-message access), (4) `GET /api/alerts/rule-stats` all-time query (no limit at all, relies on implicit PostgREST default cap), (5) `GET /v1/alerts/history` (50-row hard cap, no pagination), (6) `GET /v1/webhooks/deliveries` (50-row hard cap, no pagination), (7) `GET /v1/admin/service-health` summary branch (1000-row hard cap feeding a 24h count that could undercount).
- **Unknown/edge-case rows: 2** — `GET /api/signals` relevance-blend mode at very large candidate counts, `GET /v1/signals` (backend) relevance-blend mode on the public API beyond page 1.
- **Ok rows:** the remainder — properly paged (`.range()` loop), explicitly bounded-and-disclosed, backed by a real enforced application cap, or not a list/DB query at all.
