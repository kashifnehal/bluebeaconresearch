### v0.32.0 — 3 live production map-page bugs from a screenshot report (2026-08-28)

All three were reported from a real production screenshot; all three confirmed and fixed live against a dev server + throwaway Supabase test account (`36b522a`).

- **Map tiles showing CARTO's "API KEY REQUIRED" watermark — root cause confirmed platform-wide, not project-specific.** Curled `basemaps.cartocdn.com/dark_all/{z}/{x}/{y}.png` directly (bypassing the app entirely) and got the same watermarked tile back. Grepped the whole repo for any CARTO API key/env var — none exists and never has. So this isn't an expired key, wrong env var name, or a usage cap tied to our traffic; CARTO deprecated anonymous/keyless access to this raster CDN account-wide, and the project was always using it unauthenticated. Rather than sign up for a CARTO account blind, switched `apps/web/lib/map-config.ts`'s `BASEMAP_TILE_URLS` to Esri's `World_Dark_Gray_Base` service — free, no key, no signup, purpose-built for dark dashboard basemaps. Verified live: clean tiles, correct attribution, no watermark.
- **Signal map popup rendering with a white background instead of the app's dark theme, fixed.** `buildSignalPopupHTML()` never set a background — it inherited `maplibre-gl.css`'s hardcoded `.maplibregl-popup-content { background: #fff }`. A first override placed in `globals.css` at normal cascade priority silently did nothing; root cause was that Next/Turbopack emits `globals.css` and `maplibre-gl.css` as separate chunks and always links the maplibre-gl chunk *after* globals.css in the HTML, regardless of `@import` order in source — so cascade order can't be relied on to beat this specific vendor stylesheet. Fixed with `!important` on the popup content/tip overrides, using the app's existing `#131313`/`#3c4a42` dark tokens (matching `--bg-primary`/`--border`, already used elsewhere e.g. `.map-vignette`). Verified live via a real popup click.
- **"Ingestion Delayed" banner's "Next run ~X ago" copy — confirmed genuine cadence degradation, not a mislabel.** Checked real `raw_events` timestamps rather than guessing: sustained ~60min gaps between successful GNews/GDELT inserts over the past 24h against a stated 15min cron, and a live 99min gap at investigation time (last successful fetch 07:00 UTC, checked at 08:39 UTC). The banner's underlying math was already correct — `nextFetchEstimate` was genuinely in the past — the copy just read confusingly ("~6 minutes ago" for a *next* run). Reworded `IngestionStatusBanner.tsx` to say "overdue by ~X" when the estimate has passed. **Not fixed, flagged as separate follow-ups requiring a decision:** (1) RSS collector produced **zero** `raw_events` rows in the last 24h (GDELT/GNews are the only sources landing anything) — root cause not diagnosed, this task was scoped to the banner copy, not the pipeline; (2) the ~60min-not-15min real cadence is consistent with GNews's free-tier daily request quota (`~96 req/day at 15-min intervals` per the code's own comment) being exhausted mid-day, but this wasn't confirmed against a real production API key (none available in this environment) — needs either a paid GNews tier, a longer cron interval, or accepting the degraded cadence as-is.

### v0.24.0 — Upstash Redis Quota Exhaustion: Root-Cause Fix, Not Just a Cap Increase (2026-08-19)

- **Context**: Upstash's 500,000-command quota was fully consumed (confirmed live: `Limit: 500000, Usage: 500003`), producing a continuous `ReplyError: ERR max requests limit exceeded` storm in the workers service logs, severe enough that Railway itself started dropping log messages. Investigated as three compounding sources, fixed all three — evaluated for 10x/100x/1000x traffic, not just today's founder-only load.
- **Part 1 — Dormant BullMQ workers gated off**: `apps/backend/src/workers/{ai-classifier,signal-generator,alert-dispatcher}.ts` each instantiate a `Worker` (no `QueueEvents` anywhere in the codebase) that polled Redis continuously with nothing feeding them jobs — per ADR 006, the real collectors classify+insert directly, bypassing BullMQ. Gated behind `ENABLE_BULLMQ_WORKERS` (default off) in `apps/backend/src/workers.ts`; dormant code preserved, matching the comment pattern already used at `ai-classifier.ts`. Verified live: `dev:workers` now logs "BullMQ workers disabled" and instantiates none.
- **Part 2 — Backoff added to the shared ioredis client**: `apps/backend/src/clients/redis.ts` had no custom `retryStrategy` (ioredis's default caps reconnect at 2s and retries forever) and no protection against a burst of command-level failures compounding. Added a bounded `retryStrategy` (capped at 15s) and a circuit breaker: once 5+ Redis errors cluster within 10s (tracked across both client-level `'error'` events and per-command failures reported by call sites via the new exported `recordRedisError()`), disconnects outright and returns `null` from `getRedis()` for a 60s cooldown instead of retrying into the same failure.
- **Part 2b — unplanned but load-bearing finding**: `@fastify/rate-limit` (`apps/backend/src/app.ts`) was configured with the shared Redis connection as its store, running a Lua `eval`/`evalsha` on *every single incoming backend request* — including Railway's own `/health` probe, which has no rate-limit exemption. Worse, a Redis failure here wasn't handled gracefully — it propagated and 500'd the entire request before reaching any route handler. This was very likely the largest single driver of quota consumption, independent of user count. Switched to the plugin's default in-memory store. Also fixed `apps/backend/src/routes/prices.ts`'s two handlers, which threw uncaught on a Redis failure instead of reaching their own already-written DB fallback — now catch, report to the breaker, and fall through correctly. Verified live: `/health` and `/v1/prices` both returned correctly (200 / expected auth response) against the still-exhausted production quota, where they previously 500'd.
- **Part 3 — Web rate limiter's local fast-path logic was backwards**: `apps/web/lib/ratelimit.ts` only skipped the external Upstash REST call once a key was *already over* its limit — normal traffic (the common case) round-tripped to Upstash on every request. Inverted: now resolves fully from local memory unless a key is within 20% of its limit or hasn't synced with Upstash in the last 10 requests / 5 seconds (whichever first) — a **periodic reconciliation** design, not accepted under-enforcement, chosen specifically because Vercel runs `apps/web` as multiple non-memory-sharing instances (see `10_DECISIONS.md` for the full trade-off writeup). Verified via a standalone logic test: 9 consecutive under-limit requests resolved with zero calls to the Upstash branch; local-only blocking at the configured limit still works with zero Upstash dependency, unchanged from before.
- **Part 4 — `RATE_LIMIT_SAFE_MODE` confirmed, not touched**: when set, `rateLimitOrPass()` returns success immediately for every call, before even touching the local bucket or Upstash — a full bypass of both, for all 4 routes that call it (`/api/prices`, `/api/prices/history`, `/api/backtesting`, `/api/signals`). This is an emergency valve, not a long-term stance — it removes abuse protection entirely and should come back off once real user traffic exists. Founder action item, not set here: `RATE_LIMIT_SAFE_MODE=true` on Vercel.
- **Part 5 — Second Redis connection, investigated and explained (not a bug)**: two genuine, distinct sources of a second physical connection exist, both legitimate ioredis/BullMQ architecture, not leftover/duplicate-singleton bugs: (a) `apps/backend/src/routes/signals.ts`'s `/stream` SSE route calls `pub.duplicate()` per client connection (required since pub/sub needs a dedicated connection separate from the command connection) — properly `unsubscribe()`+`quit()`s on client disconnect, and gated to `pro`/`api` plan tier only; (b) BullMQ itself internally duplicates the shared connection for each `Worker`'s blocking read — expected, unavoidable BullMQ behavior, now moot by default since Part 1 gates the workers off.
- **Part 6 — Growth visibility**: piggybacked a reactive Redis-quota check onto the existing `workers:heartbeat` cron (every 5 min) — logs a greppable `[REDIS QUOTA]` warning at 70%/90%, parsed directly from Upstash's own error string (`Limit: X, Usage: Y`), the only usage signal available with this project's current credentials (confirmed live: neither the per-database REST API's response headers nor ioredis's `INFO` command expose usage; Upstash's account-level Management API, which would allow *proactive* pre-failure percentage checks, needs `UPSTASH_API_KEY`+`UPSTASH_EMAIL`, not present in `.env.local` — founder action item if wanted). Rough post-fix command budget and "users supported before quota upgrade" estimate documented in `08_CURRENT_STATUS.md`.
- **Verified live throughout** against the real, still-exhausted production quota (not a simulated failure) — every fix in Parts 1–3 and 2b was smoke-tested against the actual live `ERR max requests limit exceeded` condition, not reasoned about abstractly.
