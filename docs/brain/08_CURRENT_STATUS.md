## QA-Batch Investigation Pass: Relevance Filter, Map Tab, Notification Status (2026-08-25)

Three items from the same external QA pass as the 2026-08-22 batch, each requiring live reproduction before fixing (per the task's own instructions — not accepted as "guessed and tightened"):

- **P0 — Intelligence Feed surfacing irrelevant content at 95% confidence.** Root-caused with hard evidence, not assumption: traced 32 real irrelevant production `signals` rows through the actual `matchesKeywords()`/`shouldExclude()` functions (not a description of them). **Confirmed it's entirely the keyword pre-filter (`apps/backend/src/lib/relevance-filter.ts`), not the Claude classification step** — confidence values (0.92 for real geopolitical signals, 0.95 for junk) look like genuine, correctly-reasoned Claude output in both cases; Claude is correctly recognizing junk has "no financial market impact," it's just being asked to classify content that should never have reached it. Concrete matched-keyword evidence: `"dow"` substring-matched any word containing "down" ("Downers Grove", "chase down"); `"russell"` matched the name "Russell T Davies"; `"business"`/`"economic"`/`"economy"`/`"financial"`/`"finance"`/`"corporate"` matched routine local content ("grows new microgreen business"); `"military"` matched fitness/history/hall-of-fame content; `"deal"`/`"bank"`/`"market"`/`"options"`/`"rally"`/`"dollar"` all had confirmed generic-word false positives. Checked `corn`/`gold` specifically (flagged as suspect in the source audit) against two separate real-data queries and found **zero** false positives for either — left unchanged rather than guessing. Fixed (`b0783ab`): narrowed/removed the confirmed offenders, added precise multi-word `EXCLUDE_KEYWORDS` phrases for recurring noise patterns (farmers markets, Dollar Tree, military fitness/history/hall of fame, celebrity net worth, sports trade deadlines, Revolutionary War monuments), and added compensating phrases (`trade deal`, `peace deal`, `nuclear deal`, `arms deal`, `world bank`, `stock options`, `dow jones`, `russell 2000`) so real signal isn't lost. **A second, more severe bug was found live while sanity-checking the fix**: `shouldExclude()` used plain substring matching, so the `"nfl"` hard-exclude (meant only for NFL sports content) was silently matching inside **"inflation"**, **"conflict"**, and **"influence"** — three of the most important terms for this exact product — with zero trace, since filtered items are never logged anywhere. Fixed in the same commit by switching `shouldExclude()` to the same `\b`-boundary regex `EXACT_WORD_KEYWORDS` already used. **Verified**: the same 33-title reproduction set (32 unique + 1 dup) drops from 33/33 passing (100% false-positive rate on this adversarial sample) to 8/33 (24%) after the fix; 9/9 genuine geopolitical/macro headlines (Iran, tariffs, OPEC, Houthi, Fed inflation) still pass correctly, including a headline that was previously silently dropped by the `nfl`/`inflation` bug. 7-day DB baseline before the fix: 8.1% of all signals (43/532) matched the severity=1 + confidence≥0.9 junk signature. Residual known gaps, deliberately not chased further to avoid losing real recall: bare `war`/`military`/`china`/`trade`/`market`/`silver` still allow a handful of low-volume false positives (an HBO WWII miniseries, K-pop military service, a sports column literally titled "Stock Market").
- **P0 — Event Detail page's Map tab rendering empty.** The task's own brief was right that this needed live Playwright, not more code reading — `EventLocationMap.tsx`'s worker-URL fix and `resize()` call were both already correct, and no console/network errors ever fired (the MapLibre worker and CartoDB tiles all loaded with `200`s). The real bug was one level up, in the shared `components/ui/tabs.tsx` primitive: its Tailwind classes used the attribute-*presence* variant `data-horizontal:flex-col`, but Base UI's `Tabs.Root` actually sets `data-orientation="horizontal"` — never a bare `data-horizontal` attribute — so the variant never matched and the Tabs root stayed permanently `flex-row` (the CSS default), squeezing the content-panel wrapper toward zero width for any tab content with no intrinsic text-based sizing to prop the row open. Confirmed via direct DOM measurement: the Map tab's panel measured `{w: 3.55px, h: 2px}`, with the MapLibre canvas inside collapsed to `{width: 2, height: 300}` — the map was genuinely initializing and loading real tiles into a functionally invisible 2px-wide canvas. Text-heavy tabs (Analysis/Historical/Sources) happened to look fine because their own paragraph text's min/max-content width propped the same broken row layout open regardless — only the Map tab's empty ref-sized `<div>` had nothing to contribute, which is why it's the one that visibly "rendered empty." Fixed (`bb8335c`): switched all four occurrences of the same `data-horizontal`/`data-vertical` mismatch (Root, `TabsList`, `TabsTrigger` ×2) to Tailwind's `data-[orientation=...]` attribute-*value* selector. This UI primitive is used in exactly one place in the app (`events/[id]/page.tsx`), so the fix has zero blast radius elsewhere — confirmed via a repo-wide grep before touching it. Live-verified both branches: a signal with precise `lat`/`lng` now renders real tiles, place labels, and the marker pin; a signal with `null` coordinates correctly shows the "Approximate location" fallback centered over the continental US, also with real tiles.
- **P0 — Notification bell showing undelivered alerts as delivered.** This one arrived pre-root-caused (traced in a prior session): `alert-dispatcher.ts` correctly writes a real `status` (`"queued"`/`"delivered"`/`"failed"`) per `alerts_sent` row; the bug was that `/api/alerts/recent` already selected `*` (status was always in the payload) but `NotificationPanel.tsx` never read it, so a queued or failed alert rendered identically to a genuinely delivered one. Chose to keep the query unfiltered and render a distinct visual state (amber "Not Delivered" / red "Delivery Failed" badge + one-line explanation) rather than filtering server-side, since silently hiding a fired-but-undelivered alert leaves a trader with no way to notice their rule isn't actually reaching them — filtering it out would have been the easier fix but a worse product decision. **`alerts_sent` is currently empty in production (0 rows)** — this bug is real in the code but hasn't visibly manifested yet since no alert has ever actually been dispatched. Live-verified anyway by inserting two throwaway rows (queued + failed) against a real signal for the logged-in test account, confirming both render distinctly in the actual bell UI, then deleted them. Fixed and verified in `3c2378c`.

## Upstash Redis Quota Exhaustion — Root-Caused & Fixed (2026-08-19)

Upstash's 500,000-command quota was fully exhausted (`Usage: 500003`, confirmed live), causing a `ReplyError` storm severe enough that Railway started dropping its own log messages. Root cause was **three compounding sources**, not one — fixed all three rather than just raising the ceiling. Full detail: `14_CHANGELOG.md` v0.24.0.

1. **`@fastify/rate-limit` (`apps/backend/src/app.ts`) was Redis-backed and ran a Lua `eval`/`evalsha` on every single incoming backend request — including Railway's own unauthenticated `/health` probe.** This was almost certainly the single largest driver: constant, request-volume-scaling load with no relation to real users, and worse, when Redis failed, `@fastify/rate-limit` propagated the error instead of failing open, 500ing the *entire* API on every request until Redis recovered. Switched to the plugin's default in-memory store (correct today at Railway's `numReplicas: 1`; would under-count per-instance if this service is ever horizontally scaled — revisit then).
2. **Three BullMQ `Worker`s (`ai-classifier.ts`, `signal-generator.ts`, `alert-dispatcher.ts`) polled Redis continuously with nothing ever feeding them jobs** (per ADR 006, collectors classify+insert directly, bypassing BullMQ). Flat, constant cost regardless of user count. Gated behind `ENABLE_BULLMQ_WORKERS` (default off); dormant code preserved, not deleted.
3. **`apps/web/lib/ratelimit.ts`'s local fast-path had the logic backwards** — it only skipped the Upstash REST call once a key was *already over* its limit, so normal traffic (the common case) round-tripped to Upstash on every request. Inverted: now resolves entirely from local memory unless a key is near its limit or due for a periodic reconcile (every 10 requests or 5s per key) — sub-linear in request volume, not zero-Upstash (documented trade-off, see `10_DECISIONS.md`).

Also added: a bounded reconnect backoff + circuit breaker in the shared ioredis client (`apps/backend/src/clients/redis.ts`) so a sustained failure can't compound into a retry storm again, and a reactive quota-usage check piggybacked on the existing `workers:heartbeat` cron (logs a greppable `[REDIS QUOTA]` warning at 70%/90%, parsed from Upstash's own error string — true *proactive* percentage checks need `UPSTASH_API_KEY`/`UPSTASH_EMAIL` for Upstash's account-level Management API, not present in this project's env; founder action item if wanted).

**Rough post-fix command budget** (reasoned estimate from actual call patterns, not measured): fixed/cron cost ≈ **~1,000 Redis commands/day** at near-zero traffic (mostly price-syncer's Redis cache writes on the 15-min ingestion cron, ~768/day, plus pipeline-status bookkeeping, ~192/day). Per-active-user cost ≈ **~10–40 commands/day**, dominated by the web rate-limiter's periodic reconcile touches across `/api/signals`, `/api/prices`, `/api/prices/history`, `/api/backtesting` (a dashboard kept open and polling most of a day). At that rate, **the current 500K/day quota supports on the order of 10,000+ active users/day** before needing a plan upgrade — assuming per-user usage stays similar to the founder's own testing pattern (mostly dashboard polling, not heavy API-tier usage). Sanity-check this against real numbers once there's real traffic; this is a planning estimate, not a measurement.

## 3. How the Data Pipeline Works

```
Railway workers (startup + every 15m)
  RSS (BBC, Al Jazeera, Guardian, NPR, UN News) + GNews + GDELT
        ↓
isRelevantEvent() word-boundary filter — ~70% of articles filtered out
        ↓
Deduplicate by external_id — most remaining articles already in DB
        ↓
Insert into raw_events + signals (event_date = article PUBLISH time)
        ↓
Next.js /api/signals (default feed: 24h fresh + active ongoing events; explicit `window=latest|24h|7d|active` filters available)
        ↓
Dashboard shows eventDate → "X hours ago" = when article was PUBLISHED
```

## 4. Why Dashboard Timestamps Look "Old" (Not a Bug)

| Field        | Meaning                                   | Shown in UI?                     |
| :----------- | :---------------------------------------- | :------------------------------- |
| `created_at` | When **we ingested** the signal           | ❌ No (except NotificationPanel) |
| `event_date` | When the **source article was published** | ✅ Yes — `"12 hours ago"`        |

A signal ingested **5 minutes ago** from a BBC article published **12 hours ago** will display **"12 hours ago"**. Refreshing the page does not change this — it is intentional (v0.10.0 decision).

Featured cards on `/alerts` pick the first signal with **`severity >= 8`**. New ingested signals with lower severity (e.g. 5) exist in the DB but may not become the hero card.

## 6. How to Verify Workers Are Healthy

Railway → **workers** → Logs. Expect:

```
Running initial ingestion immediately on startup...
startup:rss → { inserted: N, signals: N, ... }
workers: cron schedulers active, health server listening
workers:heartbeat → every 5 min
rss-collector / price-sync → every 15 min
```

Supabase SQL:

```sql
SELECT title, created_at, event_date,
       NOW() - created_at AS ingested_ago,
       NOW() - event_date AS published_ago
FROM signals ORDER BY created_at DESC LIMIT 5;
```

If `created_at` advances but UI still shows old times → check `event_date` (publish time), not ingestion.
